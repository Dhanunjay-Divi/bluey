# Design — redundant per-turn context (send-once fix)

> Research + design output of workflow wf_a74a2c17-702. No code changes; this is the plan.

## Verdict

TWO DISTINCT PROBLEMS, only one is a true bug. (1) TRUE BUG — redundant prior-conversation replay on a resumed turn: on the CLI native-resume path (drive/cli.rs:335 calls render_prompt() unconditionally, even when q.resume is set), and on any ACP fork-fallback turn, Bluey re-prepends the whole 'Context from a prior conversation:' meeting blob every message even though the vendor already holds that history via --resume. tier.rs correctly suppresses its OWN continuation transcript (Channel B) on true ACP resume (tier.rs:246 leaves question.context unset), but it never CLEARS the SEPARATE meeting context (Channel A) that app.rs:7231 already packed into question.context before apply_tier ran — so on the CLI drive that Channel A survives and is rendered every turn. This is genuine double context and it is what leaks Bluey's git-status scaffolding chatter (which lives in the meeting transcript / recent-Q&A, i.e. Channel A) into the model each turn. (2) SEPARATE, PARTLY-INTENDED WASTE — the meeting context (brief + pinned-decisions ledger + summary + last-N transcript + recent Q&A + artifacts) is rebuilt and attached on EVERY ask because the only gate is `if request.context.is_empty()` (app.rs:6571) and the overlay ask path always constructs a fresh empty-context request. There is NO first-turn detection anywhere (confirmed). Sending the pinned ledger + newest transcript every turn is partly BY DESIGN (a mid-meeting decision must survive past the last-N window and past vendor compaction), but re-sending the full brief + old transcript + Q&A verbatim every turn is waste and is the bulk of what the user sees repeated.

## Trace (where the redundancy is)

There are TWO independent context channels that both flow into the agent prompt, and only one of them is suppressed on a resumed turn — and only on the ACP path.

CHANNEL A — MEETING context (brief + verified ledger + pinned decisions + summary + transcript + recent Q&A + artifacts). Built by answer_context_from_meeting (app.rs:9028) via answer_context_for_question (app.rs:8811). Gated by `if request.context.is_empty()` at app.rs:6571. On the overlay ask path (OverlayEvent::AskRequested, app.rs:2438 → answer_request_from_overlay) the request is freshly constructed with an EMPTY context every turn, so that gate is ALWAYS true and the WHOLE meeting package is rebuilt and attached on EVERY ask. This is NOT tier-aware: it happens before resolve_answer_route/answer_with_agent/apply_continuation_tier ever run.

CHANNEL B — CONTINUATION context (the prior-session transcript). Handled by tier.rs apply_tier. For NativeResume + ACP + cwd usable (Claude App case) it correctly sets question.resume and leaves question.context UNSET (tier.rs:245-247) — it does NOT attach the prior transcript. So Channel B is correctly suppressed on a true ACP resume.

THE BUG: Channel A and Channel B are separate. apply_tier only governs Channel B. Channel A (meeting brief/ledger/transcript) is packed into question.context by agent_question_from_payload (app.rs:7216, loop at 7231 over payload.context) BEFORE apply_continuation_tier runs (app.rs:7384). The ACP-resume tier branch never CLEARS an already-populated question.context; it only refrains from setting its own. So question.context still holds the full meeting blob.

WHY THE USER SEES IT DIFFERS BY DRIVE PATH:
- ACP path (acp/drive.rs:74-76): on resume it sends `bare = question.prompt` and does NOT send render_prompt() — so on a TRUE ACP resume the meeting blob in question.context is effectively DROPPED (only used as fork_prompt fallback if session/load fails). So a clean ACP true-resume should NOT re-send the blob.
- CLI path (drive/cli.rs:335): ALWAYS calls q.render_prompt() regardless of q.resume, so a non-ACP native `--resume` (Claude CLI) DOES prepend the entire "Context from a prior conversation:" meeting blob every turn.
Therefore the user's observed every-turn "Context from a prior conversation:" blob (with Bluey's own git-status scaffolding chatter — that chatter lives in the meeting transcript / recent Q&A, i.e. Channel A) is the MEETING context via render_prompt_within (drive/mod.rs:138-189, framing string at :146/:170), re-sent because (a) it is rebuilt every turn at app.rs:6571-6573 and (b) it is rendered every turn on the CLI drive path — OR on a fork-fallback ACP turn. It is NOT the continuation transcript from tier.rs (that one is correctly suppressed on ACP true-resume).

### Redundancy sites

- `crates/cue-daemon/src/app.rs:6571` — The ONLY context gate is `if request.context.is_empty()` — on the overlay ask path the request is always fresh/empty, so this is true every turn and the entire meeting context package is rebuilt on every ask. No first-turn check.
- `crates/cue-daemon/src/app.rs:8816` — answer_context_for_question → answer_context_from_meeting: the whole package (brief + verified ledger + pinned decisions + summary + transcript + recent Q&A + artifacts) is assembled unconditionally each call; nothing knows it was already sent last turn.
- `crates/cue-daemon/src/app.rs:9028` — answer_context_from_meeting builds brief (9036), pinned decisions ledger (9054), summary (9062), last-N transcript (9077-9085, incl. Bluey's own git-status scaffolding chatter), recent Bluey Q&A (9087-9094) — the exact 'Context from a prior conversation' body the user sees repeated.
- `crates/cue-daemon/src/app.rs:7231` — agent_question_from_payload packs every payload.context item (the meeting Channel A) into question.context BEFORE apply_continuation_tier runs — so meeting context is already in question.context regardless of tier.
- `crates/cue-daemon/src/app.rs:7384` — apply_continuation_tier is called AFTER question.context is already populated (7361) and only governs the continuation transcript (Channel B); it never clears the pre-loaded meeting context on a resumed turn.
- `crates/cue-agent-bridge/src/continuation/tier.rs:246` — ACP true-resume branch leaves question.context unset (suppresses Channel B) but does NOT clear the meeting context already sitting in question.context — the gap that lets Channel A survive onto a resumed turn.
- `crates/cue-agent-bridge/src/drive/cli.rs:335` — CLI drive calls q.render_prompt() UNCONDITIONALLY (regardless of q.resume), so on a non-ACP native --resume the full meeting-context blob is prepended to the prompt on every turn.
- `crates/cue-agent-bridge/src/drive/mod.rs:138` — render_prompt_within flattens question.context into the 'Context from a prior conversation:\n...\nQuestion:\n' blob (framing at :146/:170) — the literal string the user reports seeing re-sent every message.

### First-turn gap

NONE. There is no first-turn detection anywhere in the code. The only context gate is `if request.context.is_empty()` (app.rs:6571), and on the overlay ask path the request is always constructed fresh with empty context (OverlayEvent::AskRequested at app.rs:2438 → answer_request_from_overlay), so the gate is true EVERY turn and answer_context_for_question rebuilds the entire meeting package (brief + ledger + decisions + summary + transcript + recent Q&A + artifacts) on every single ask. Nothing tracks whether this is the first turn of a resumed session, and nothing suppresses/diffs Channel A (meeting context) after the first turn. The session-id chaining logic (app.rs:7826-7850, DriveOutcome.session_id persisted as attached_session) advances the resume target turn-to-turn but carries NO signal that context was already delivered — apply_tier and the meeting-context builder never consult it for a first-turn decision.

## Design (the 4 fixes)

CHOSEN DESIGN = (a) as the primary fix + a scoped (b) for the first-turn "meeting brief once" split. Reject full (b) generality and (c) for v1.

=== WHAT CHANGES, WHERE (no code, just the edits) ===

FIX 1 — PRIMARY, tier-aware: stop rendering the meeting blob on a NativeResume turn where resume is actually active. Touch point: crates/cue-agent-bridge/src/drive/cli.rs:335. Today it calls q.render_prompt() UNCONDITIONALLY. Change: when q.resume is Some (native --resume active), send the BARE prompt (q.prompt), NOT render_prompt() — mirror exactly what acp/drive.rs:66-76 already does (bare on resume, full render only as fork fallback). This is the single highest-value edit: it makes the CLI native-resume path behave like the ACP path, which the trace confirms already drops the blob on true resume. Rationale: the vendor CLI reloads its own transcript on --resume (verified for Claude/Codex/Copilot); re-prepending Channel A is pure duplication.

FIX 2 — clear pre-loaded meeting context in the tier branches that own history. Touch point: crates/cue-agent-bridge/src/continuation/tier.rs, the two NativeResume-with-resume-active branches (ACP true-resume ~245-247 and non-ACP native ~259-264). Today they set question.resume but leave a pre-populated question.context (the meeting Channel A packed at app.rs:7231) intact. Change: in BOTH resume-active NativeResume branches, explicitly set question.context = None (or an incremental delta, see FIX 3) once resume is committed. This makes tier.rs the single authority that guarantees "resume active ⇒ no replayed context", instead of relying on each drive path (cli vs acp) to independently remember to drop it. With this, FIX 1 becomes belt-and-suspenders (render_prompt with None context already returns bare prompt per mod.rs:140), but keep FIX 1 too so a stray context set elsewhere can't leak.

FIX 3 — first-turn "send heavy context ONCE" marker (scoped (b)) for the ONE thing resume does NOT carry: the MEETING context. The vendor session holds prior AGENT turns, but Bluey's meeting brief/ledger/transcript is NOT in that session on turn 1 of an attach. So: TURN 1 of an attached session → send full Channel A once; TURNS 2..N → send only the new question + a small delta (new ledger decisions + transcript segments since last ask). State home: settings.attached_session already tracks the session and is persisted in the chaining block at app.rs:7826-7850 (with the still_attached guard). Add a sibling persisted marker there — e.g. settings.attached_context_primed: bool (or store the high-water marks: last_sent_transcript_seq / last_sent_decision_id). Set it in the SAME persist call that advances attached_session (app.rs:7839 persist_attached_agent + the ledger append at 7861). Consume it at the context-build gate app.rs:6571: change `if request.context.is_empty()` to also require "not yet primed for this attached session" for the HEAVY parts (brief + summary + full transcript + Q&A), while STILL sending the always-pinned delta (new decisions + new transcript tail) every turn. Concretely, split answer_context_from_meeting (app.rs:9028) into (i) a heavy first-turn package and (ii) a light per-turn delta, selected by the primed marker. When attached_session is None/new or primed=false → full package + set primed. When primed=true → delta only.

FIX 4 — volatile-prefix hygiene (do regardless of tier). Touch point: answer_context_from_meeting transcript block (app.rs:9077-9085) and Recent Bluey Q&A (9087-9094). Strip Bluey's own scaffolding chatter (git-status recitations, internal Q&A echoes) from what gets replayed — it is the visible junk the user is complaining about and it also poisons the vendor's own prompt-cache prefix. This is a filter on last_transcript_text_bounded / last_conversation_text inputs, not a structural change.

=== TIER MATRIX AFTER FIX ===
- NativeResume + resume active (Claude CLI/Agent-SDK, Codex, Copilot, Cursor-ledger-gated) via ACP OR CLI: question.context = None (FIX 2), bare prompt sent (FIX 1/acp already). Meeting Channel A sent ONCE on turn 1 via the primed marker (FIX 3), delta-only after.
- NativeResume degraded to Replay (cwd missing, tier.rs:265-277) and true Replay (tier.rs:278-290): unchanged behavior — they legitimately replay the continuation transcript because no vendor session absorbs it. But they STILL benefit from FIX 3 (meeting Channel A once) and FIX 4 (de-scaffold). Note: the user's LIVE bug (Claude *App*/cloud session) resolves to one of these Replay-class paths in practice (cloud history is not local), so FIX 3+4 are what actually fixes what the user sees; FIX 1+2 fix the true-CLI-resume case.

=== WHY NOT (c) FOR v1 ===
(c) rolling-summary for Replay adds a summarize-drive per turn (cost, latency, a place to lose the pinned ledger) and duplicates what maybe_compact already does at the char cap. Defer. FIX 3's snapshot-then-delta already removes the bulk of Replay waste without holding a summary.

Smallest correct change = FIX 1 + FIX 2 (kills the confirmed redundant-transcript-on-resume) plus FIX 3's marker (kills the every-turn heavy meeting rebuild) plus FIX 4 (kills the scaffolding chatter the user literally sees). FIX 1+2 are ~10 lines and fully tier-aware; FIX 3 is the only one that needs new persisted state, and it reuses the existing attached_session persist site.

## Risks

- DOUBLING-BUG REGRESSION (the exact hazard tier.rs:230-234 warns about): if FIX 2 clears context but a code path still renders the transcript, or if FIX 1 is applied without FIX 2 and some other site sets context, the agent sees history twice and echoes old answers. Apply FIX 1 and FIX 2 together and keep render_prompt's None-context bare-prompt behavior (mod.rs:140) as the backstop.
- LOSING MID-MEETING DECISIONS: if FIX 3 stops re-sending the pinned decisions ledger after turn 1, a constraint agreed at minute 5 falls out of the agent's context by minute 40 (the ledger exists precisely because the last-N transcript window drops it). Mitigation: the delta on turns 2..N MUST still include new/changed pinned decisions; only the BRIEF + old transcript + Q&A become first-turn-only.
- PINNED-BRIEF-SURVIVES-COMPACTION CONTRACT: answer_context_from_meeting deliberately pushes brief+ledger FIRST so compact_provider_context (which drops in INSERTION ORDER) can't evict them; there's a 'before-the-transcript' regression test. Splitting into first-turn vs delta packages must preserve that insertion-order-first invariant in BOTH packages or the test breaks and the brief becomes evictable.
- FIX 4 over-stripping: a too-aggressive scaffolding filter could remove legitimate user/agent transcript turns, degrading answer quality. Filter must target Bluey's OWN emitted chatter (git-status recitations, Bluey Q&A echoes) narrowly, not general transcript content.
- The primed marker is persisted settings; a crash between the drive answer and persist_attached_agent (app.rs:7839) could leave primed=false while the vendor already has history — causing one extra full-context resend. Acceptable (idempotent, just wasteful once), but note it.

## Research: CLI resume behavior (per agent)

### How CLI coding agents handle multi-turn context on resume (per-agent), and what it means for Bluey's double-context bug

CORE FINDING (holds for ALL six agents): The underlying LLM API is stateless, so *someone* must replay the full message history to the model on every turn. But for every one of these CLIs, that replay is INTERNAL to the CLI. Each CLI persists its own transcript to local disk and, on `--resume <id>`, RELOADS that transcript itself, then appends only the caller's new prompt. The caller (Bluey) passes ONLY the new message. So Bluey re-sending its "Context from a prior conversation:" blob to a NativeResume agent's --resume path is genuine DOUBLE context: the vendor already holds and replays the history, and Bluey stuffs a second, redundant copy (plus its own scaffolding chatter) into the new prompt. Confirmed for the specific case the user hit (Claude): the docs show `claude -p --resume <session-id> "summarize what we changed"` — the only thing the caller supplies is the new prompt string.

PER-AGENT (question 1: does CLI reload its own transcript so you send only the new prompt? / question 2: where is state stored? / question 3: resume vs replay cost):

CLAUDE CODE CLI (--resume / --session-id, incl. `claude -p --resume`): (1) YES — CLI reloads its own stored transcript; caller sends only the new prompt. Docs: "Sessions are saved continuously to local transcript files as you work"; resume example passes only the follow-up prompt. (2) ~/.claude/projects/<project-slug>/<session-id>.jsonl (JSONL, one line per message/tool-use/metadata; format is internal + version-unstable — do NOT parse it directly, use /export or --output-format json). Session-ID lookup is SCOPED TO THE ORIGINAL PROJECT DIRECTORY + its git worktrees; resuming from the wrong cwd yields "No conversation found with session ID" (this matches Bluey's memory that cwd is the path resolver for Claude resume). (3) Resume is NOT free: the CLI replays the whole conversation to the model each turn (linear->effectively quadratic token growth), but Anthropic prompt-caching (cache-read ~$0.30/M vs input $3/M on Sonnet) + auto-compaction blunt it. Known gotcha: resuming long sessions replays opaque thinking-block signatures (~25% of resume payload, ~156K tokens before you type) — invisible cost that Bluey ADDING its own blob only worsens.

CODEX CLI (codex exec resume <id> / --last / --all): (1) YES — "Accepts an optional follow-up prompt"; Codex restores prior message history + plan history + approvals from disk; caller supplies only the new instruction. Model's in-context state does NOT persist — it's reconstructed by re-reading the transcript. (2) ~/.codex/sessions/YYYY/MM/DD/rollout-<timestamp>-*.jsonl (full transcript incl. prompts, responses, tool calls, token usage). `--ephemeral` skips writing. (3) Same replay-from-transcript cost model as Claude; no per-id server-side model memory.

CURSOR CLI (cursor-agent --resume <uuid> / `agent resume`): (1) YES — "The task prompt is not re-sent when resuming a session"; Cursor resumes via the stored chat ID. (2) ~/.cursor/chats/ (UUID-keyed; format UNDOCUMENTED and may change — don't rely on parsing it). (3) Replay cost implied; note the chat-ID-capture mechanism is undocumented, so Bluey depending on scraping it is fragile — consistent with Bluey classing Cursor closer to needing care. NOTE: Bluey's brief lists Cursor as NativeResume; the vendor DOES hold history on --resume, so the redundant-blob logic applies to Cursor too when a real session id is available.

GITHUB COPILOT CLI (copilot --resume <id> / --continue / in-session /resume): (1) YES — "When you resume a session, Copilot loads the full conversation history, so you can continue exactly where you left off." Caller sends only the new prompt. (2) ~/.copilot/session-state/<session-id>/ holds the full session (conversation, tool calls, files touched, permissions granted) as files, PLUS a local SQLite "session store" (a subset) that powers /chronicle and cross-session Q&A. (3) Standard replay-from-store; local only (no cross-environment resume yet — local<->Codespace resume is an open feature request).

GEMINI CLI (--resume / -r, /chat save|resume): (1) YES — session history recorded automatically in the background; --resume loads the most recent (or picker-selected) session; caller continues with only new input. (2) ~/.gemini/tmp/<project_hash>/chats/ (project-scoped; switching project dir switches history). Separately, file-modifying tool approvals create Git checkpoints in a shadow repo ~/.gemini/history/<project_hash>. 30-day default retention. (3) Replay cost model; project-hash scoping means, like Claude, cwd/project identity matters. IMPORTANT: Bluey classes Gemini as REPLAY tier. Gemini CLI in interactive/normal use DOES have local session resume — but whether Bluey can drive it by session id headlessly is the open question; if Bluey has no id handle into Gemini's own store, replay is indeed unavoidable for Bluey even though Gemini itself stores history.

ANTIGRAVITY / agy CLI (--conversation / -c, /resume, /fork): (1) YES — "Every conversation you have with agy is saved to the session store, not just the messages, but the agent's working state"; --conversation resumes by ID. (2) Local session store keyed by Conversation ID; /fork copies a conversation into a new workspace. (3) Resuming long/old sessions is explicitly "not free" — reloads accumulated (possibly stale/contradictory) context. KEY GAP for Bluey: headless `--print` mode did NOT emit the per-conversation ID needed for callers to resume a specific session (open feature request #7 on google-antigravity/antigravity-cli) — this is likely WHY Bluey correctly treats Antigravity as REPLAY: no id reaches Bluey, so no native resume, so replay is forced.

WHY THE TWO TIERS ARE RIGHT, AND WHERE THE BUG IS: The NativeResume/Replay split is fundamentally about whether Bluey can obtain and pass a resumable session ID into the vendor's own store — NOT about whether the vendor stores history (they ALL do locally). Claude/Codex/Copilot expose a stable resumable id -> NativeResume is correct. Cursor exposes a UUID but capture is undocumented/fragile. Gemini + Antigravity store history but don't reliably hand Bluey a per-session id for headless resume -> Replay is the correct fallback.

**Applies to Bluey:** For NativeResume agents (Claude CLI/App/Agent, Codex, Copilot, and Cursor when a real session id exists): the vendor CLI already reloads its OWN stored transcript on --resume and replays it to the model — Bluey passes only the new prompt. Therefore apply_tier's `question.context` blob ("Context from a prior conversation:") is REDUNDANT double context on every resumed turn and should NOT be sent when question.resume is set. Fix: add first-turn detection — send full context ONCE on the FIRST dispatch of a session (before any resumable id exists), then on subsequent turns set only question.resume + the new message and DROP question.context entirely. This also stops leaking Bluey's own scaffolding chatter (git-status recitations) into the model, and avoids compounding the known thinking-signature/replay token bloat. For true Replay agents (Antigravity, Gemini when no id handle, Aider, Windsurf, VS Code): no session id reaches Bluey so replay is unavoidable — BUT sending the identical full blob every turn is still wasteful; prefer a held/rolling summary + only-new-message, and strip Bluey's internal scaffolding from the replayed transcript. Concretely this means threading a per-session "first turn / has-resumable-id" flag into apply_continuation_tier (~app.rs:7264) and answer_context_from_meeting (~8816/~9028) so context is built once, not every ask; answer_context_for_question (~6572) already guards on request.context.is_empty(), which is the right shape to generalize.

### How production multi-agent orchestrators & meeting-copilots avoid re-sending full context every turn ("send once, then incremental") — and the concrete fix for Bluey's NativeResume path.

There are THREE distinct patterns in production, and they map cleanly onto whether the sender owns the model API or drives an external agent. Bluey's agent path is the third case.

=== PATTERN 1: STATEFUL SESSION — the id IS the context (this is Bluey's case) ===
When something else (a vendor/CLI/server) holds the conversation history, you resume by id and send ONLY the new message. The history is never re-sent over the wire.

- Claude Code CLI (definitive, from code.claude.com/docs/en/sessions + /headless): history is auto-saved append-only to ~/.claude/projects/<encoded-cwd>/<session-id>.jsonl. To continue, you run `claude -p --resume <session-id> "new message"` — Claude Code loads the FULL prior history from that JSONL file itself; the caller passes only the new prompt. The session id + correct cwd is sufficient to restore everything (messages, tool calls, results). You do NOT, and should NOT, re-attach the transcript. Resume lookup is scoped to the working directory / git worktrees ("No conversation found with session ID" if cwd is wrong).
- OpenAI Responses API (developers.openai.com/api/docs/guides/conversation-state): pass `previous_response_id` (~60 bytes) + only the new user message; the server keeps the context. IMPORTANT caveat that maps to Bluey: `previous_response_id` does NOT carry over top-level *instructions/system prompt* — those must be re-sent each turn. So even in the pure-stateful world, the split is: stable-context-and-history = held server-side (send once), but the system/instruction layer is re-sent.
- This is exactly what real coding orchestrators do. Vibe Kanban (BloopAI) passes `--resume <old-session-id>` to the claude binary and relies on the vendor's on-disk history — it does not resend a transcript blob. (Their known bug, issue #2993, is instructive: when the worktree path changes, the ~/.claude/projects/ key changes, resume fails, and — the tell — they do NOT fall back to re-sending the transcript; they just error. Confirms the resume-by-id model is the whole mechanism.) Claude Squad / Conductor follow the same "spawn Claude Code instances in worktrees, resume by id" model.

=== PATTERN 2: PROMPT CACHING — cache the stable prefix, pay ~10% on re-reads (this is what you do IF you call the model API directly) ===
When YOU own the API call and must resend history each turn (stateless HTTP), you don't avoid resending — you make resending cheap by caching the stable prefix.
- Anthropic prompt caching (platform.claude.com/docs/en/build-with-claude/prompt-caching): mark a cache breakpoint; everything up to it is cached 5 min (or 1h TTL at 2x write). Cache reads cost ~10% of normal input; cache writes ~25% premium. ~90% discount on the stable portion.
- The multi-turn recipe: cache the system prompt + injected context ONCE, and mark the LAST message block with cache_control each turn so the breakpoint walks forward. Turn N reads system+turns[1..N-1] from cache and only fully processes the newest user message. Token usage splits into cache_read_input_tokens / cache_creation_input_tokens / input_tokens.
- HARD REQUIREMENT: the cached prefix must be BYTE-IDENTICAL across turns. Any timestamp, reordered tool list, or shuffled context injected into the prefix busts the cache. (This is directly relevant to Bluey: today's blob re-embeds volatile scaffolding — git-status recitations — which would be cache-poison even if Bluey did cache.)

=== PATTERN 3: CLIENT-SIDE INCREMENTAL / DELTA + ROLLING SUMMARY (meeting-copilot memory management) ===
For long-running conversation memory where you can't rely on a vendor session (meeting assistants, LangChain-style memory):
- Snapshot-then-delta: send full state once (or infrequently), then append only deltas; concatenate deltas in order (AG-UI / ADK state_delta pattern).
- Rolling/hybrid summary (ConversationSummaryBufferMemory): keep the last ~5-8 turns verbatim + a running summary of everything older; when the buffer overflows, the oldest turns get summarized and merged. Combined production stack = sliding window (recent verbatim) + rolling summary (older) + retrieval (beyond window). This is the standard answer to "40 turns × 200 tokens = 8k tokens of overhead before you type anything." Meeting tools (Granola/Otter/Fireflies) publish no engineering detail confirming a specific approach — the searchable material is feature/pricing-level only — so cite them only as the product category, not as a verified implementation.

=== THE STANDARD "SYSTEM + LONG CONTEXT ONCE, THEN DELTAS" DESIGN ===
Combining the above, the industry-standard shape is a THREE-LAYER prompt split:
1. Stable system/instructions layer — re-sent every turn (Responses API won't carry it; caching makes it cheap). Must be volatile-free.
2. Context/history layer — sent ONCE, then held (vendor session by id, or server cache, or client-side summary). NOT re-sent verbatim.
3. Delta layer — only the new user message (+ any genuinely new facts) each turn.
The bug is always #2 being re-sent verbatim every turn; the fix is always to move #2 behind a session id, a cache breakpoint, or a rolling summary.

**Applies to Bluey:** Bluey's agent path drives an EXTERNAL CLI (Claude App/CLI/Agent, Cursor, Copilot, Codex) — it does NOT call the model API directly. So Pattern 2 (prompt caching) and Pattern 1's Responses-API variant are NOT levers Bluey holds; the vendor's own client owns caching/session. That means the correct fix for NativeResume is Pattern 1 in its purest form:

1) THE PRIMARY FIX — for a NativeResume agent, do NOT attach ANY prior-conversation context when resuming by id. The vendor holds the history (Claude Code loads it from its own JSONL via `--resume <session-id>`; this is verified). apply_tier already sets question.resume for NativeResume — the bug is that answer_context_from_meeting still builds and attaches the full "Context from a prior conversation:" blob EVERY ask, and render_prompt_within still wraps it. When question.resume is set (i.e. we successfully resumed a real vendor session id), question.context should be EMPTY. The vendor already has turns 1..N-1; re-sending them is pure redundancy AND actively harmful (it duplicates history the model already sees, and it leaks Bluey's own scaffolding chatter — git-status recitations — into the prompt). This is precisely how Vibe Kanban/Claude Squad/Conductor behave: resume by id, send only the new message.

2) THE FIRST-TURN CAVEAT — there is a real "send once" split even here, and it mirrors the OpenAI `previous_response_id` caveat (instructions don't carry over). Bluey's meeting-derived context is NOT part of the resumed vendor session, so:
   - TURN 1 of a resumed/att­ached session: send the full brief + decisions ledger + transcript context ONCE (this is the meeting context the agent has never seen).
   - TURNS 2..N: send ONLY the new user message plus, at most, an INCREMENTAL delta of what changed since the last ask (e.g. "new decisions since last turn:" from the ledger, and only transcript segments newer than the last ask). Not the whole brief/ledger/transcript again.
   This requires first-turn detection, which the code does NOT have today (verified: answer_context_for_question only skips rebuild when request.context.is_empty(), and answer_context_from_meeting rebuilds unconditionally). Concretely add per-(agent-session) state tracking: a flag "brief already delivered to this session id" + a high-water mark (last transcript segment index / last ledger decision id sent). This is the snapshot-then-delta pattern (Pattern 3).

3) VOLATILE-PREFIX HYGIENE (do this regardless): strip Bluey's own scaffolding (git-status recitations, internal chatter) out of whatever context IS sent. Even in a Replay agent (where re-sending is unavoidable), a byte-stable, chatter-free prefix is the precondition for the vendor's OWN prompt caching to hit — volatile junk in the prefix busts caching downstream and wastes the user's tokens.

Net: NativeResume → context = empty on resume (id carries history); the only "send once" you owe is the meeting brief/ledger on the FIRST turn of a session, then deltas. Replay agents legitimately still resend (no id reaches Bluey), but should resend a de-scaffolded, stable, ideally summary-compacted context so the vendor's caching works.

### CLI-vs-GUI session persistence per agent, and whether Bluey's CLI-driven "resume" can actually land in a GUI-created session (with per-agent CLI-can-reach-GUI-session verdicts)

## Framing

A "session" only round-trips through Bluey's NativeResume path if BOTH are true: (a) the session's history lives in a store the CLI Bluey drives can read, and (b) the CLI's `--resume <id>` resolves to that store's id-space (for Claude/Agent-SDK, resolution is cwd-scoped: id + encoded cwd → JSONL path). If either fails, "attach GUI session + send" is not a resume — it silently becomes replay-into-a-fresh-session (or, worse for cwd-scoped agents, a wrong-cwd empty mint). This is exactly the class of failure the tier.rs logic already guards for Cursor via the ledger gate.

The GUI surfaces split cleanly into two kinds, and this is the whole answer:
  - GUI = another local process over the SAME local file store (Cursor IDE, Antigravity desktop, Codex IDE extension) → reachable in principle IF the CLI's id-space maps to it. In practice each vendor SILOS the CLI store from the IDE store even though both are local.
  - GUI = a CLOUD/server-side product (Claude desktop app, Claude Code web, ChatGPT/Codex cloud) → the history never touches the local store the CLI reads, so the CLI can NEVER reach it. This is categorical, not a bug.

## Per-agent

### Claude — THE live bug's agent
- Claude Code **CLI** and the **Claude Agent SDK** ("agent mode") share ONE local store: `~/.claude/projects/<encoded-cwd>/<session-id>.jsonl`. Same cwd → same bucket; `--resume <id>` / `session/load` resolves there. This is precisely the NativeResume path tier.rs already banks on (the doc comment at tier.rs:227-234 is correct). CLI ↔ Agent-SDK: fully reachable.
- Claude **desktop app** is an Electron wrapper over claude.ai; its conversations are held **server-side in Anthropic's cloud**, NOT in `~/.claude/projects/`. Claude Code **web** and the VS Code extension likewise each keep their own history. There is no local JSONL for a desktop-app chat, and open GitHub issues (anthropics/claude-code #28791, #56038) exist *specifically requesting* CLI↔desktop↔web sync because it does not exist today.
- **CLI-can-reach-GUI(desktop-app)-session = NO** (cloud-held, categorically unreachable by a local `--resume`). CLI-can-reach-Agent-SDK-session = YES.
- IMPLICATION FOR THE LIVE BUG: when the user "resumes a Claude App session," Bluey is NOT doing a true native resume into that desktop chat — it cannot, the history isn't local. It is running the Replay path (re-send the transcript blob) OR minting a new local CLI session. That is why the whole "Context from a prior conversation:" blob (scaffolding chatter included) re-appears every turn: there is no vendor-held session absorbing the history, so render_prompt_within re-emits it each ask. The doubling the user sees is the honest signature of replay-mislabeled-as-resume. This should be classified as Replay for the Claude *App/web* surface, distinct from Claude Code CLI/Agent-SDK which are genuine NativeResume.

### Codex
- Codex **CLI** writes every session to local JSONL at `~/.codex/sessions/`; `codex resume <id>` / `--last` reads it. The Codex **IDE extension** (VS Code / Cursor) uses the SAME local files — CLI ↔ IDE-extension is genuinely shared and cross-continuable.
- Codex **cloud** tasks run in OpenAI-hosted containers; the **ChatGPT desktop app** is a separate cloud product. Native CLI sessions are NOT surfaced as first-class threads in Codex desktop/cloud history (open request: openai/codex #21079), and cloud task state is not a local JSONL the CLI resumes by id.
- **CLI-can-reach-IDE-extension-session = YES; CLI-can-reach-ChatGPT-desktop/cloud-session = NO** (cloud-held / not exposed to the CLI id-space).

### Cursor
- OFFICIAL confirmation (Cursor moderator, community forum thread 159779): "CLI sessions and editor sessions are stored separately and don't sync across surfaces." The IDE keeps chats in per-workspace SQLite (`workspaceStorage/<hash>/state.vscdb`, `~/.cursor/chats/*/store.db`) behind a separate INDEX; `cursor-agent --resume <chat-id>` lists only CLI-created chats, and copying files into `~/.cursor/chats` does nothing because the IDE reads its own index, not raw transcripts. Both stores are LOCAL, yet disjoint.
- **CLI-can-reach-IDE-session = NO** (separate local stores + separate id-space). This VINDICATES the existing `resume_requires_ledger` gate: a Cursor IDE chat-id fed to `cursor-agent --resume` silently mints an empty session (exit 0) — exactly the failure tier.rs:157 degrades to Replay to avoid.

### Antigravity
- The `agy` **CLI** persists each conversation to its own local session store and resumes via `agy --conversation=<id>` (alias `-c`) / the `/resume` picker. The **desktop app** (Antigravity 2.0, Windsurf-lineage IDE) keeps its own store. Marketing claims a shared "agent harness/runtime" and that sessions "can be exported terminal↔desktop," but export ≠ a shared live id-space: an unassisted `agy --conversation=<desktop-id>` does not land in the desktop conversation. This matches the user's established finding that agy CLI and desktop stores are disjoint.
- **CLI-can-reach-desktop-session = NO** (disjoint stores; at best an explicit export step, not an id-resume). Confirms the prior verdict; Antigravity is correctly Replay + fork-only.

## Honest UX for the NO cases (Claude App/web, Codex ChatGPT-desktop/cloud, Cursor IDE, Antigravity desktop)

For every "NO" surface, "attach a GUI session and continue it" is physically Replay, not resume. The honest posture:
1. Do NOT present these as "resumed" — label the surface as Replay in the UI, distinct from the CLI/Agent-SDK surfaces that are true NativeResume. The agent-surface split the user already tracks (Claude 3 rows, Codex/Cursor separate CLI vs GUI surfaces) should carry a per-surface reachability flag, not a per-agent one — the CLI row and the GUI row of the SAME vendor can have opposite verdicts (Claude, Codex, Cursor all do).
2. Since these are Replay, the doubling bug fix is the SAME everywhere: send the full "Context from a prior conversation:" blob ONCE on the first turn of the Bluey-held continuation, then only the new user message thereafter — because there is no vendor session absorbing history, Bluey's own bridge session IS the memory, so re-emitting the whole blob every turn is pure redundancy (and leaks Bluey's scaffolding chatter each time). There is currently NO first-turn detection in the code (confirmed), which is why it re-sends every turn. First-turn detection belongs in the Replay branches of apply_tier / answer_context_from_meeting, keyed on whether this bridge session has already emitted its context blob once.
3. Only the genuine NativeResume surfaces (Claude Code CLI, Claude Agent SDK, Codex CLI, Codex IDE-extension) should ever set question.resume and suppress the context blob — and there tier.rs already correctly leaves context unset (no doubling). The bug is confined to the Replay-class surfaces being driven as if a first-turn-once policy existed when it does not.

**Applies to Bluey:** Add a per-SURFACE (not per-agent) reachability flag. NativeResume is only ever valid for Claude Code CLI, Claude Agent SDK, Codex CLI, and the Codex IDE-extension — all four share a local file store whose id-space the CLI's --resume resolves (cwd-scoped for Claude). Every GUI/cloud surface — Claude desktop app, Claude Code web, ChatGPT/Codex cloud, Cursor IDE, Antigravity desktop — is UNREACHABLE from the CLI (cloud-held, or a disjoint local store with a separate id-space) and must be treated as Replay. The user's live bug is a Claude *App* (cloud) session mislabeled/driven as resume: its history is not local, so Bluey is really replaying, and with NO first-turn detection in the code it re-sends the entire context blob (scaffolding included) every turn. Fix = in the Replay branches only, emit the full context blob ONCE per bridge session (first turn), then send only the new message; leave the true-NativeResume branches untouched (tier.rs already suppresses context there, no doubling).
