# LockedIn to Bluey gap map

## Reading the status

Status is from Bluey's perspective against LockedIn's **statically observed and narrowly runtime-confirmed** implementation:

- `Bluey stronger`: Bluey has a materially safer or more complete implementation in the compared domain.
- `Equivalent`: both have comparable implemented primitives, with stated caveats.
- `Partial`: Bluey implements part of the LockedIn capability or has a less productized path.
- `Missing`: no comparable Bluey implementation was found. This does not automatically mean Bluey should build it.

LockedIn evidence is linked through this folder. Exact Bluey source locations are consolidated in [bluey-code-map.md](evidence/bluey-code-map.md).

## Risk synthesis

- **Security:** LockedIn's runtime renderer sandbox is a verified mitigation, but its broad preload bridge, tracker-bearing privileged renderer, permissive navigation/transport posture, token-bearing protocol URL/argument logging, and remote-input executor would expand Bluey's trusted computing base. Bluey's narrow browser sandbox, egress guard, short ticket, encrypted profile, and submit journal are the safer Jobs reference design (`jobs/browser/src/main.ts:94-120,405-430`; `jobs/browser/src/browser-network.ts:18-53`; `jobs/browser/src/protocol.ts:1-20`; `jobs/runner/src/crypto-envelope.ts:7-167`).
- **Privacy:** LockedIn can process continuous audio, screen, documents, transcript/history, helper events, and billing identity while loading several attribution vendors. Runtime consent, retention, and deletion cascades are unknown. Bluey should retain explicit screenshot approval and interview-prep PII filtering (`crates/cue-daemon/src/app.rs:3174`; `jobs/automation/src/interview-prep.ts:344-372`).
- **Scalability:** LockedIn's client exposes reconnect/reload/session checks but no observable durable worker protocol. Bluey's lease, replay-safe discovery, and irreversible-submit boundaries are suitable for horizontal workers (`jobs/workflows/src/discovery.ts:320-418`; `jobs/runner/src/execution-lease.ts:27-159`; `jobs/browser/src/irreversible-submit.ts:6-175`).
- **Reliability:** LockedIn has useful bounded renderer/audio recovery, but architecture-specific native packaging is asymmetric and the update channel permits downgrade/prerelease. Bluey should borrow failure-test ideas, not binaries or update policy.
- **Maintenance/provenance:** LockedIn packages 49,270 ASAR entries, native modules, and many third-party web scripts; its source licenses/SBOM were not supplied. Any code reuse is rejected pending ownership, license, dependency, and provenance review.

## Recommended priority for Bluey

### P0: preserve safety and close current boundaries

1. Keep Bluey's browser sandbox, public-network guard, tenant/identity profile encryption, short run-ticket protocol, irreversible-submit journal, and intervention approval model unchanged.
2. Make long-lived desktop tokens Keychain-backed by default and add redaction tests for deep links, arguments, and logs (`crates/cue-cloud-client/src/tokens.rs:1-6,72-115`).
3. Complete one production email/calendar provider only after the OAuth, webhook, encryption, replay, and deletion release gates pass (`jobs/ARCHITECTURE.md:85-96`).

### P1: small product-quality adaptations

1. Build the existing screenshot-capture dashboard surface around Bluey's current user-approved capture APIs (`crates/cue-daemon/src/app.rs:2186-2193,3174,13941-14055`).
2. Add evidence-grounded post-interview reports from Bluey's transcript/recap/interview-prep artifacts, with source links and PII exclusions.
3. Add scoped interview presets and priority questions without granting renderer IPC or remote OS-control authority.
4. Expose receipt verification/export and side-effect-unknown reconciliation in the Jobs portal.

### P2: validate before committing

1. Research whether a view-only helper mode solves a real collaboration need. Do not begin with remote keyboard/mouse control.
2. Add typed, signed rollout flags if operational complexity justifies them.
3. Add monotonic signed desktop auto-update only after stable-channel and rollback testing.

## Reuse and provenance decision

No LockedIn code, binary, configuration value, asset, or dependency bundle should be copied into Bluey. Ownership of the DMG authorizes inspection, not automatic relicensing. Before any reuse, Bluey needs ownership confirmation, dependency license/SBOM review, source provenance, third-party notice review, and a clean-room decision.

Product concepts suitable to **adapt** from observed behavior are scoped interview presets, priority questions, post-session reports, and a polished user-approved screenshot flow. Patterns to **reject** are generic preload IPC, tracker-loaded privileged renderers without CSP, token-bearing deep links/argument logging, unrestricted external URLs/ATS, downgrade-enabled auto-update, and remote OS input without a separately designed authorization boundary.

## Concrete handoff

The next implementation agent should not port LockedIn code. It should select one Bluey-owned P1 slice, preferably the screenshot dashboard or evidence-grounded post-interview report, write the product contract and threat model first, and implement only against existing Bluey audio/screenshot/transcript/receipt primitives. Acceptance criteria must include source provenance, explicit consent, PII filtering, private local storage, no new generic IPC, no third-party renderer scripts, and tests for cancellation/restart/deletion.
