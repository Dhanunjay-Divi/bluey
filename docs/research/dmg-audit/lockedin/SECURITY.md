# LockedIn security assessment

## Scope

This assessment combines read-only static inspection with one separately authorized, isolated, unauthenticated launch from the read-only image. Findings describe observable attack surface and missing client-side controls; they do not assert exploitation. Server controls may reduce risk but were not supplied. Runtime used no credentials, clicks, permission grants, updater/install, helper, or remote-control action, and external egress was blocked. Evidence and unknowns are indexed in [evidence/README.md](evidence/README.md), [runtime-unauthenticated.md](evidence/runtime-unauthenticated.md), and [limitations.md](evidence/limitations.md).

## Verified protective controls

- The bundle is Developer ID-signed, hardened-runtime enabled, notarized, and has a valid stapled ticket; strict deep signature verification succeeded ([bundle-identity.txt](evidence/bundle-identity.txt)).
- Main and auxiliary BrowserWindows disable Node integration and enable context isolation (`app.asar:public/electron.js:811-1033`); runtime confirmed the renderer process also had `--enable-sandbox` ([runtime evidence](evidence/runtime-unauthenticated.md)).
- Content protection is wired to stealth state, crash uploads are disabled, renderer/audio recovery is bounded, and the app uses a single-instance lock ([electron-main-observations.md](evidence/electron-main-observations.md)).
- Every packed ASAR entry passed its integrity digest. Unpacked signed Mach-O hash differences are explainable by post-package signing and do not override the successful code signature ([asar-inventory.txt](evidence/asar-inventory.txt)).

## Findings

| Priority | Observed fact | Risk and boundary | Recommendation |
|---|---|---|---|
| High | Preload exposes generic `send/on/invoke/removeAllListeners` wrappers, and corresponding main handlers do not visibly validate sender origin (`public/preload.js:124-140`; [preload evidence](evidence/preload-ipc-observations.md)). | A renderer compromise can reach a much broader main-process capability set than a narrow contextBridge contract would expose. Exploitability depends on renderer compromise and handler validation. | Replace generic wrappers with per-capability methods and typed schemas; verify sender frame/origin and session capability in every privileged handler. |
| High | The renderer accepts WebRTC `remote-control` JSON and can forward it to robotjs mouse/key/scroll execution (`public/electron.js:2935-3102`; [renderer evidence](evidence/renderer-features.md)). | This is a powerful remote OS-input boundary. Helper authorization, consent, replay protection, revocation, and audit trail are unknown. | Require explicit per-session user consent, mutually authenticated short-lived capabilities bound to peer/session, sequence/replay protection, visible control state, immediate revocation, strict event schemas/rate limits, and tamper-evident audit records. Do not enable by default. |
| High | `build/index.html` has no static CSP and directly loads Stripe, Clarity, Rewardful, GTM, and LinkedIn scripts in the privileged renderer. | Third-party supply-chain or injected script execution could inherit the broad preload bridge. A server CSP might exist, but this local `file:` document has no response header. | Remove trackers from the privileged renderer or isolate them in an unprivileged webview/window; ship a deny-by-default CSP with nonces/hashes and a narrow connect allowlist. |
| Medium | Runtime confirms the Electron renderer sandbox is active, but the app has no macOS App Sandbox entitlement and retains JIT/unsigned executable memory/library-validation exceptions plus screen/audio/input capabilities. | The Electron sandbox is a real mitigation. The native main process and broad IPC/entitlement surface still make renderer-to-main compromise consequential. | Preserve the active renderer sandbox, isolate native/media functions behind narrow brokers, remove unused entitlements, and document/test every remaining entitlement. |
| High | Protocol URLs contain `firebaseCustomToken`; main code logs process information including full `argv` (`public/electron.js:2218-2234,2466-2585`). Runtime confirmed full argument logging to a `0644` main log, though the disposable parents were `0700` and contained no token. | Token-bearing deep links can be exposed in process lists or logs. A mode-0644 log is readable by other local users if production parent directories are traversable. | Return an opaque one-time code plus state/PKCE, exchange it over an authenticated channel, redact URL/query/argv values everywhere, write logs `0600`, and expire/reject replayed codes. |
| Medium | `openExternal` accepts any nonempty renderer-supplied URL without a scheme/host allowlist (`public/electron.js:3328-3338`). | A compromised renderer could invoke non-HTTPS custom schemes or unexpected local handlers. | Parse and allow only explicit HTTPS hosts plus audited first-party schemes; reject credentials, file/data/javascript URLs, malformed URLs, and private-network targets. |
| Medium | No `setPermissionRequestHandler`, `setWindowOpenHandler`, or `will-navigate` controls were found. | Browser permission/navigation policy appears to depend on defaults and UI conventions; new windows/navigation can widen renderer reach. | Deny permissions and window opens by default; allow only exact media permissions in the expected frame and block navigation away from the packaged app. |
| Medium | Info.plist permits arbitrary loads and local networking and includes TLSv1.0 localhost exceptions. | This expands the set of destinations/transports available to compromised renderer/native code. Static production URLs were mostly HTTPS, so plaintext use is not proven. | Remove global arbitrary-load permission, require modern TLS, and grant only the smallest localhost exception if a documented feature needs it. |
| Medium | Updater enables prerelease and downgrade releases, auto-download, install-on-quit, and checks mutable `latest` metadata. Runtime attempted the check and created `.updaterId` even with `ELECTRON_NO_UPDATER=1`; the closed proxy blocked every response/download/install. | A signing-key/release-channel compromise or unintended downgrade has a broad automatic blast radius. Electron signature checks may mitigate package tampering, but policy remains permissive and the common suppression variable did not stop the explicit app call. | Pin stable channel, disable downgrades/prereleases in production, require monotonic versions and expected signing identity, provide a documented enterprise/offline disable control, protect metadata with an authenticated update framework, and log only redacted state. |
| Medium | Default Electron session is shared by main/document windows; no `safeStorage`, Keychain, or app-specific encrypted local store was found. Runtime created Cookies, IndexedDB, Local/Session Storage, Trust Tokens, caches, updater ID, and logs before authentication. | Tokens, Firestore persistence, helper flags, prompts, and logs may be recoverable from the user-data directory after authenticated use. The isolated Chromium database files were `0600`; main log/updater ID were `0644` under `0700` parents. | Partition least-privilege windows, minimize persistence, move refresh/long-lived secrets to Keychain, set every sensitive file `0600`, and implement complete local sign-out/deletion cleanup. |
| Medium | `.env.local` is bundled in the ASAR. | Every recipient can extract every value. Firebase/Clerk public configuration is expected to be public, but this packaging cannot protect any server secret accidentally added later. | Treat all renderer configuration as public, prohibit secret variables in desktop builds with CI scanning, and issue short-lived server-side credentials when needed. |
| Medium | Firebase Auth deletion is visible, but cascading Firestore/object/backend/analytics/local deletion is not established. | Users may interpret account deletion as complete erasure when the client only proves identity deletion. | Make deletion a server-orchestrated, idempotent workflow with provider cleanup, status/receipt, retention exceptions, and local cache wipe. |
| Low/compatibility | Packaged `MacKeyServer` is x86_64-only, while inspected PDF native modules are arm64-only. | Native paths may fail on one architecture or trigger translation/security maintenance complexity. Runtime reachability is unknown. | CI-test every reachable native module on both architectures, remove unused binaries, and sign/notarize architecture-complete artifacts. |

## Privacy observations

The product can process microphone/system audio, screen captures, documents/resumes, transcript/chat history, helper invitations, billing identity, and post-session survey data. The renderer also includes multiple analytics/attribution vendors. The isolated unauthenticated launch created ordinary Electron persistence but, because egress was blocked and no account was used, did not validate tracker payloads or consent. Static/runtime resources still do not prove data minimization, authenticated retention, subject-access export, regional routing, or tracker opt-out. Network origins and storage paths are in [DATA-AND-NETWORK.md](DATA-AND-NETWORK.md).

## Bluey security implications

Bluey should reuse none of the bundled code without ownership, license, dependency, and provenance review. Product concepts may be evaluated, but the following patterns should be rejected:

- generic renderer-to-main IPC;
- token-bearing deep links and unredacted argument logging;
- third-party trackers in a privileged local renderer without CSP;
- unrestricted external URL handling and broad ATS;
- remote OS input without a dedicated, authenticated capability design;
- downgrade/prerelease auto-update policy in production.

Bluey already has stronger building blocks for the Jobs domain: sandboxed controller windows and network egress guards (`jobs/browser/src/main.ts:94-120,405-430`; `jobs/browser/src/browser-network.ts:18-53`), minimal run tickets (`jobs/browser/src/protocol.ts:1-20`), tenant/identity-scoped encrypted profiles (`jobs/runner/src/profile-store.ts:17-70`; `jobs/runner/src/crypto-envelope.ts:7-167`), and irreversible-submit journals (`jobs/browser/src/irreversible-submit.ts:6-175`). The smallest safe course is to preserve these boundaries and adapt only narrowly specified UX ideas.

One Bluey hardening opportunity remains independent of LockedIn: Bluey's default cloud token store writes raw tokens to a mode-0600 file, with Keychain opt-in (`crates/cue-cloud-client/src/tokens.rs:1-6,72-115`). Moving long-lived secrets to Keychain by default would improve the comparison.
