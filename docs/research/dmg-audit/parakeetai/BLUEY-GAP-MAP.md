# ParakeetAI → Bluey gap map

## Baseline and status meanings

Parakeet evidence is the exact DMG fixed by [hashes.txt](hashes.txt). Bluey evidence was revalidated at Git commit `eb923a89f24b69664c73479607bf665725789658`; the normalized line map is [bluey-code-map.txt](evidence/bluey-code-map.txt).

- `Bluey stronger`: Bluey's source implements a materially safer or more complete form of the capability.
- `Equivalent`: both have a comparable static implementation, though details differ.
- `Partial`: Bluey has a relevant implementation but is narrower, disconnected, or not production-complete relative to the observed Parakeet flow.
- `Missing`: no corresponding Bluey implementation was found.

Statuses describe source at the inspected commit, not deployed availability.

## Security, privacy, scalability, and maintenance conclusions

**Security.** Parakeet's strongest positive signals are signing/notarization, local renderer loading, content protection, and `safeStorage` use for one ancillary secret. Its generic IPC, non-HttpOnly session cookies, bearer deep link, URL JWT, broad ATS/entitlement surface, and media permission handler should be rejected as Bluey patterns. Bluey must still audit its own broad default Tauri plugin permissions rather than assuming framework choice provides least privilege. [SECURITY.md](SECURITY.md)

**Privacy.** Parakeet sends live audio to Speechmatics, session/chat content to its service, and operational identifiers to Mixpanel; server retention and deletion are unknown. Bluey has explicit account deletion and receipt-grounded interview prep that excludes contact/demographic/calendar-attendee data. Any new live-session handoff should reuse that sanitized packet boundary, not raw Jobs workspace records.

**Scalability/reliability.** Parakeet's client-side action serialization, session heartbeat/takeover, and bounded audio recovery are useful product patterns but reveal no durable backend design. Bluey's Jobs leases, workflow IDs, immutable submit marker, encrypted result envelope, and side-effect-unknown state are materially stronger for automation. Meeting-session takeover, if needed, should use a separate lightweight server lease rather than reuse a job execution lease blindly.

**Maintenance.** Parakeet ships minified Electron bundles, a native Rust/NAPI layer, four platform binaries, and a pinned Git audio dependency. Copying creates ownership/license/update risk and imports Electron-specific boundaries into Tauri/Rust. Requirements can be adapted clean-room; code reuse is rejected pending provenance review.

## Recommended P0/P1/P2 changes

### P0 — preserve and tighten trust boundaries

1. Do not copy any Parakeet resource or source. Record this DMG/hash as research provenance and require ownership/license/SBOM review before reconsidering.
2. Audit `crates/cue-dashboard/capabilities/default.json`: remove default filesystem/dialog/shell/updater access not required continuously, split high-risk operations by window/command, validate every payload, and add deny-path tests. Parakeet demonstrates why a locally packaged renderer still needs least privilege.
3. Verify Bluey's browser-link exchange server-side for one-time consumption, state/PKCE, replay rejection, audience/device binding, and log redaction. The UI already indicates a minted code (`crates/cue-dashboard/ui/src/pages/Onboarding.tsx:55-65`); make those invariants tested rather than assumed.

### P1 — smallest production-quality product improvements

1. **Jobs-to-live-session handoff.** Add a typed command/API accepting the existing `InterviewPrepPacket`, enforce application/receipt/resume consistency exactly as `jobs/portal/src/lib/interview-prep.ts:28-100` does, strip contact/demographics/attendees, and attach source IDs to generated responses. Do not create a second resume/document ingestion path.
2. **Dashboard analyze-screen.** Connect the dashboard placeholder to Bluey's existing screenshot service with preview/confirm, window/region selection, 10-image and byte/dimension bounds, ephemeral transfer, metadata stripping, and a visible data destination.
3. **Meeting signal adapter.** Replace/augment the frontmost-app heuristic with clean-room macOS and Windows active-microphone adapters in an isolated helper. Return only a recognized-app enum and active timestamp; do not retain arbitrary process lists. Keep the current heuristic as fallback and test permissions/CPU/false positives.
4. **Echo cancellation.** Implement an audited backend behind `AudioCaptureConfig.echo_cancellation`, which already exists but defaults false. Benchmark system-loopback + microphone double-talk, latency, CPU, and failure fallback before enabling by default.

### P2 — useful parity after the P1 foundations

1. Add opt-in automatic cue generation with one in-flight request, configurable cooldown, unmistakable active/paused status, and post-answer feedback.
2. If Bluey permits the same live session on multiple devices, add generation-fenced session ownership: atomic claim, heartbeat, stale expiry, explicit compare-and-swap takeover, and an interruption event. Do not implement it only in renderer state.
3. Complete inbox/calendar provider authorization and event workers before changing the current beta copy; retain external IDs, idempotent cursors, least scopes, deletion and rate-limit tests.
4. Add privacy-safe operational metrics for capture/STT recovery without transcript, screenshot, token, job, or email content; document retention and deletion propagation.

## Concrete implementation handoff

The next implementation agent should begin with P1 item 1 because Bluey already owns both halves and it avoids importing competitor code:

1. Define a versioned `LiveInterviewContext` generated from `InterviewPrepPacket`, containing application/job/receipt/resume IDs, sanitized role snapshot, verified claim text/IDs, supported questions, truth-gap warnings, and optional interview time—no contact data, demographic answers, inbox subjects/bodies, or attendees.
2. Add deterministic unit tests beside `jobs/portal/src/lib/interview-prep.test.ts` proving mismatched receipt/resume/application rejection and field exclusion.
3. Add a narrow dashboard command to import that context into an active/new session; persist source IDs with the session and every generated response.
4. Extend `request_cue` context assembly in `crates/cue-dashboard/src/commands.rs:1690-1795` to use the sanitized context with explicit size bounds and precedence rules, while retaining current transcript behavior when no Jobs context exists.
5. Add end-to-end tests for correct application handoff, truth-gap wording, account isolation, deletion cleanup, and no restricted-field serialization or logs.

That sequence is the smallest cohesive bridge between Bluey's stronger evidence pipeline and its live assistant. Screenshot UI, meeting detection, and AEC can follow as independent workstreams after their security/performance acceptance criteria are written.
